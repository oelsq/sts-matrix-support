# Эталоны, нагрузка и актуальность знаний

## 1. Эталонные сценарии и реальные оценки специалистов

`config/golden-cases.json` содержит 20 кандидатных эталонов. Это требования к ответу и условия, которые нельзя терять, а не уже одобренные юристом/финансистом заключения. Ответственных специалистов назначает владелец проекта. [Лист проверки 20 сценариев](specialist-review.md) содержит вопросы, кандидатные эталоны, официальные ссылки и поля для замечаний.

```sh
python scripts/evaluate_golden.py run --output runtime/evaluation/local.json
# На VM, в контейнере с настроенным Flowise:
python /app/tools/evaluate_golden.py run --live flowise --output /app/state/evaluation/live.json
```

Отчёт содержит вопрос, кандидатный эталон, фактический ответ и найденные фрагменты с версией и ссылкой. Неисполненные модельные сценарии выделяются отдельно. Файлы сохраняются с правами 0600; их место — `runtime/evaluation`, исключённый из Git.

Специалист читает эталон и источники, проверяет применимость и исключения. Для фактического ответа выставляет три оценки 0–4: точность, полезность, сохранение исключений. Отклонённые ответы остаются в знаменателе; ответы без оценки не объявляются правильными. Общая экспертная оценка остаётся `null`, пока нет реальных подтверждений и эталона, и ответа.

Пример **для назначенного специалиста**, не команда автоматического одобрения:

```sh
python scripts/evaluate_golden.py review --case consent --kind reference --reviewer 'ФИО назначенного специалиста' --role legal_specialist --decision approved --notes 'Проверены норма, исключения и период' --output runtime/evaluation/reviews.json
python scripts/evaluate_golden.py review --case consent --kind answer --run runtime/evaluation/live.json --reviewer 'ФИО назначенного специалиста' --role legal_specialist --decision approved --scores 4,4,4 --output runtime/evaluation/reviews.json
python scripts/evaluate_golden.py run --reviews runtime/evaluation/reviews.json --output runtime/evaluation/scored.json
```

Оценка привязана к хешам вопроса, эталона, всего манифеста и документов, а также точного ответа. Изменение одного из них делает соответствующую старую оценку неприменимой. CLI сохраняет введённую оператором личность; это журнал происхождения решения, а не аутентификация диплома или учётной записи специалиста. Реестр должен быть доступен только ответственным сотрудникам.

При обычной сборке Compose служебные скрипты можно скопировать: `docker compose cp scripts/. bot:/app/tools`, затем `docker compose exec bot mkdir -p /app/config` и `docker compose cp config/golden-cases.json bot:/app/config/golden-cases.json`. В установленном образе VM они включены в выпуск. Каталог состояния VM — `/app/handoff_state`, переносимой сборки — `/app/state`.

## 2. Параллельная обработка и нагрузочные проверки

`MATRIX_REQUEST_WORKERS` по умолчанию равен 1; допустимы 1–4. Разные пользователи/комнаты могут обрабатываться одновременно. Внутри одной пары «пользователь + комната» соблюдается порядок, включая ожидание повторной попытки. Контекст текущей отправки хранится через `ContextVar`: другой обработчик не может перенаправить ответ чужому запросу. Первый замер с отдельными служебными сообщениями не показал ускорения двух обработчиков: p95 вырос с 61,6 до 68,8 секунды. После замены уведомлений индикатором набора повторный замер дал 66,4 и 38,0 секунды соответственно. Это небольшие последовательные группы по 10 запросов, не статистический SLA. Переносимая настройка по умолчанию — один обработчик; на проверенной VM можно явно включить два. SQLite хранит время приёма, начала и завершения для измерения ожидания и обслуживания. Индексы обслуживают очередь и порядок тем. Вместо отдельного сообщения «Готовлю ответ» используется временный индикатор набора: это не расходует лимит сообщений Synapse на служебный текст. Ошибка индикатора не препятствует ответу; при параллельных запросах он учитывает число активных обработок комнаты.

Локальная проверка настоящей очереди с **имитированной** задержкой генерации:

```sh
python scripts/load_test_queue.py --requests 20 50 100 --output runtime/evaluation/queue-load.json
```

Это проверка очереди/повторов, не измерение производительности модели. Отдельный `scripts/run_vm_load.py` запускается в оболочке VM с доступом к Docker, в новом отдельном каталоге stages. Повторное использование каталога с прежними результатами запрещено: чужое старое подтверждение очистки не может относиться к новым аккаунтам. Скрипт создаёт две закрытые комнаты, десять пользователей нагрузки, отдельного бота и учётную запись наблюдения. Все эти аккаунты неадминистративные. Рабочий бот не останавливается. Прогон сравнивает 10 смешанных обращений при одном и двух обработчиках, затем по два запроса от каждого пользователя: 20 обращений с ответами по проверенным фрагментам. Последняя группа не означает 20 одновременных генераций LLM. Отдельный наблюдатель сверяет содержание всех 42 окончательных ответов с автоматическими условиями кандидатных эталонов; это не экспертная оценка. В сводке сохраняются число завершений Agentflow, механизмы подготовки и сообщения об ограничении частоты, без переписки. Измеряются p50/p95 общей задержки, ожидания очереди, обслуживания, входной интервал, наблюдаемая глубина очереди, ошибки и дубли. Ограничения Synapse учитываются с `retry_after_ms`; защиту сервера скрипт не отключает.

Два дополнительных обращения отправляются при остановленном изолированном боте; после запуска и ещё одного перезапуска проверяется число окончательных ответов. Тестовые учётные записи деактивируются, временные контейнеры и файлы сессий удаляются. Если деактивация не удалась, закрытый файл учётных данных сохраняется для исправления очистки. Полные отчёты по умолчанию приватны; в Git публикуются сводные показатели без переписки и токенов.

## 3. Поиск исключений и актуальность документов

`QualificationIndex` подбирает до двух дополнительных оговорок из той же статьи того же документа и области доступа. Он применяется перед генерацией, после проверенных ответов Python. Первые три прямых попадания сохраняются, общий бюджет — восемь фрагментов. Статьи из других актов и документы с иной областью доступа не подмешиваются. Это лексический подбор контекста, а не универсальное доказательство полноты нормы.

`check_knowledge_updates.py` проверяет хеши 104 материалов и срок повторной проверки. Для банковских тарифов выбран операционный интервал 7 дней, для остальных материалов — 30 дней; это политика контроля, не установленный законом срок. Сам бот делает такую **офлайн** проверку при запуске и каждые шесть часов, сохраняя `knowledge-freshness.json` рядом с inbox. Внешних сетевых запросов в этом фоне нет; ошибка мониторинга не останавливает ответы.

```sh
python scripts/check_knowledge_updates.py --output runtime/evaluation/knowledge.json
python scripts/check_knowledge_updates.py --online labor,family,personal-law,gesv-rules-2026,bank-fees-2026,nb-faq --staging official-source-staging/20261023 --output runtime/evaluation/online.json
```

Онлайн-проверка разрешает только заданные официальные HTTPS-хосты, контролирует переходы и размер. Для новой оболочки Adilet пробует официальный старый интерфейс. JavaScript-заглушка, некомплектный текст, отменённый акт или ошибка сети не считаются успешной проверкой. Отличие байтов может быть вызвано сравнением полного текста с специально выбранной выдержкой; оно не доказывает новую редакцию. Неизменный файл тарифа также не доказывает, что каталог банка не опубликовал новый файл.

Получение страницы не изменяет `reviewed_on` действующей базы. Полные кандидаты и квитанции проверки сохраняются отдельно. Назначенный специалист проверяет дату действия, изменения, формулы/приложения и область применения:

```sh
python scripts/promote_knowledge_update.py --receipt official-source-staging/20261023/family.check.json --approval runtime/evaluation/family-approval.json --record-review --reviewer 'ФИО назначенного специалиста' --version 'Проверенная редакция' --applicability-note 'Проверенные условия и даты действия'
# Сначала проверка предложенного корпуса без переключения:
python scripts/promote_knowledge_update.py --receipt official-source-staging/20261023/family.check.json --approval runtime/evaluation/family-approval.json
# Только затем применение того же одобренного кандидата:
python scripts/promote_knowledge_update.py --receipt official-source-staging/20261023/family.check.json --approval runtime/evaluation/family-approval.json --apply
```

Перед применением проверяются хеши кандидата, одобрения и действующей записи, затем целиком загружается предложенный корпус через `KnowledgeStore`. Манифест заменяется атомарно под блокировкой; старые артефакты и манифест сохраняются. Если в записи есть исключённые статьи/пункты, дополнительно требуется осмысленный флаг `--scope-reviewed`: прежние переходные ограничения нельзя переносить без проверки. Действующий бот загружает утверждённый корпус после своего перезапуска.


## Отдельный прогон настоящей модели

`--force-model` обходит подготовленные объяснения и черновики для оценки генератора, но сохраняет уточнения, точные калькуляторы и запрет на выдумывание ответа без подходящих источников:

```sh
python scripts/evaluate_golden.py --cases config/model-challenge-cases.json run --live flowise --force-model --progress --output runtime/evaluation/model-live.json
```

Поля `model_attempted`, `model_response_returned`, `force_model_requested` и `local_mechanism` различают запрос к модели, полученный проверенный результат и локальную обработку. Отклонённый ответ не считается успешной генерацией. Это диагностический режим; обычные ответы пользователей продолжают использовать подходящий безопасный механизм.

Набор содержит 60 кандидатных вопросов, по 30 на направление; 40 вопросов не входят в прежний набор из 125, но взяты из существующих наборов поиска/полезности. Это не независимый набор, проверенный внешними специалистами. Автоматический пропуск регулярного выражения может означать как содержательный пробел, так и иной допустимый вариант формулировки; такие случаи разбираются отдельно, без объявления автоматической проверки правовой экспертизой.

## Закрытый пакет для юриста и финансиста

```sh
python scripts/specialist_packet.py --cases config/model-challenge-cases.json --run runtime/evaluation/model-live.json --knowledge offline_knowledge export --output runtime/evaluation/specialist-packet
```

Пакет содержит `review.html`, полные использованные документы `sources/` и `review-template.json` с **пустыми** решениями. Каталог имеет права 700, файлы — 600. Храните его вне Git и передавайте только назначенным специалистам. Отдельно проверяются эталон и фактический ответ: точность, полезность, исключения по шкале 0–4. Имя и роль проверяющего вводит оператор; этот CLI не удостоверяет личность.

После реальной проверки:

```sh
python scripts/specialist_packet.py --cases config/model-challenge-cases.json --run runtime/evaluation/model-live.json --knowledge offline_knowledge import --completed-template runtime/evaluation/specialist-packet/review-template.json --output runtime/evaluation/specialist-reviews.json
```

Импорт проверяет версии вопроса, корпуса и точного ответа, роль специалиста, подтверждение реальной проверки и допустимость баллов. Пока специалисты не назначены и не заполнили решения, экспертное качество остаётся **не измеренным**.

## Техническая сверка банковских PDF

`tariff_catalog.py` предназначен только для уже объявленных банковских тарифов. PDF должен быть связан с официальным каталогом того же банка, проходить проверку структуры и содержать извлекаемый текст. Поле `source_verification` сохраняет хеши каталога/PDF и явное `specialist_approval=false`. Дата технической сверки файла не является экспертным одобрением всех тарифных условий или датой введения каждой комиссии. Обновление законов по-прежнему требует отдельного процесса утверждения. Старые PDF сохраняются для отката.

Для пакета без дополнительной копии текстов ответов используйте `export --metadata-only --output ...`. В нём остаются вопросы, полные использованные документы, хеши ответов и пустые решения; специалист сверяется с исходным закрытым отчётом. Неудачная генерация не исключает вопрос из проверки эталона.

## Исправления подготовки и сравнения ответов

`prepare_model_evidence` добавляет ограниченные фрагменты с исключениями и повторно проверяет область доступа/применимость. Эту же функцию используют рабочая подготовка и принудительный модельный тест. Пропуск подготовленного ответа Python не должен одновременно убирать исключения из контекста модели.

Обновление известных графов теперь переносит также `agentMessages` первого узла черновика; модели, credentials, ID, расположение и API-защита сохраняются. Жирное выделение, перенос строки и неразрывный пробел не отменяют совпадение обязательного условия. Нормализация не удаляет слова или отрицания; независимые проверки цитат, чисел и поддержанности утверждений остаются прежними.

Для независимых синтетических сценариев доступно `run --concurrency 2` (по умолчанию 1, максимум 2). Результаты сохраняются в исходном порядке случаев, счётчики показывают фактически выполненные вызовы; параллельность не меняет очередь рабочего бота. Не обновляйте графы или образ во время прогона: прерванный раунд сохраните отдельно и запустите новый на одной версии.

[Приоритетный лист специалистам](specialist-priority-review.md) описывает предметные вопросы, форму оценки и ограничения автоматического сравнения. `config/answer-criteria-proposals.json` не подменяет исходный набор. Для сравнения на тех же приватных ответах:

```sh
python scripts/compare_answer_criteria.py --run runtime/evaluation/model-live.json --output runtime/evaluation/criteria-comparison.json
```

Выход содержит только ID, проверки и счётчики, без текстов ответов. Улучшение результата от изменения критериев нельзя приписывать модели. Применимость нормы и экспертное одобрение автоматически не устанавливаются.

## Дополнительная ИИ-сверка и новые вопросы

`review_synthetic_answers.py` выполняет дополнительную ИИ-сверку закрытого синтетического отчёта с его найденными источниками. Результат помечается `ai_source_assessment`, человеческих одобрений он не создаёт. Обоснования остаются в закрытом файле; отдельная сводка содержит только количества, публичные ID сценариев и ограниченные коды замечаний. Пустой список замечаний не доказывает правильность: проверяющая модель может ошибаться и видит только переданные фрагменты. Отклонённые черновики следует оценивать отдельно от доставленных ответов.

`config/unseen-cases-20261025.json` содержит 24 новых синтетических вопроса, сформулированных перед доработкой. Формулировки и критерии не менялись после первого прогона; одна неверная метка документа исправлена с отдельной квитанцией `unseen-cases-20261025-metadata-correction.json`. Это дополнительный набор, а не независимая экспертиза реальных обращений. Реальные переписки в него не копируются.

[Добровольная оценка полезности](feedback.md) позволяет собирать суммарную обратную связь без копии текста обращения. Она дополняет тесты и предметный разбор, не заменяя их.

## Повторный поиск и задержка доставки

Кэш результатов поиска ограничен 64 записями и 60 секундами. Он хранит копии найденных фрагментов, не готовые ответы и не историю. Ключ включает хеш точного запроса, направление, размер выдачи, экземпляр семантического индекса и календарный день. Одновременные одинаковые запросы вычисляются один раз; исключения не кэшируются. Новый экземпляр базы получает отдельный кэш.

`benchmark_retrieval_cache.py` сравнивает повторные синтетические запросы с кэшем и без него, проверяя совпадение порядка фрагментов. Его время не равно задержке ответа в Matrix. Во время паузы homeserver уже подготовленные сообщения сохраняются и не генерируются заново. Глобальная пауза не заставляет повторно забирать готовые сообщения из очереди; независимые пользователи могут продолжать подготовку. Порядок запросов одного пользователя сохраняется.

Нагрузочный отчёт отдельно учитывает `delivery_attempts`, `delivery_deferrals` и `server_rate_limits`. Последний счётчик относится к настоящим ответам HTTP 429, а не к локальной паузе. Лимиты Synapse автоматически не изменяются.
