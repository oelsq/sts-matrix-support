# Flowise для основных и дополнительных чатов Element

Multica удалена из исполняемого кода бота. На текущей VM основные юридическая и финансовая комнаты подключены к Flowise. В новой установке Flowise включается явно после подготовки сервиса и потоков; без маршрута используется прямой LiteLLM.

В комнате, подключённой к Flowise, путь запроса такой:

```text
Element → Synapse → Python-бот → поиск в локальных PDF/TXT
                            → Flowise → LiteLLM → модель
                            ← проверка ответа и цитат ←
Element ← Synapse ← оформленный ответ
```

В Flowise перенесены генерация и повторная проверка ответа моделью; текущая версия использует Agentflows V2 (см. раздел ниже). Поиск по PDF, отбор источников, форматирование, проверка цитат и передача живому сотруднику остаются в Python-боте. Документы не обучают веса модели. При отсутствии подходящих документов бот может ответить без вызова Flowise.

## Ограничение Flowise

Официальный проект [архивирован, поддержка завершена 31 августа 2026](https://github.com/FlowiseAI/Flowise/discussions/6727). Здесь закреплён образ **3.1.4** по digest. Пилот слушает только `127.0.0.1:13001`; не публикуйте его напрямую в интернете. SQLite в этом образе вызывает ошибку хранилища сессий, поэтому используется отдельная PostgreSQL.

## Установка после обычного setup.py

```bash
python3 scripts/init_flowise.py
docker compose -f docker-compose.yml -f compose.flowise.yml --profile flowise up -d flowise
docker compose cp scripts/setup_flowise.py bot:/tmp/setup_flowise.py
docker compose exec bot python /tmp/setup_flowise.py --prepare-only
```

Администратор создаётся автоматически; данные входа — в `runtime/bot/flowise_admin.json`, не в Git. Flowise открывается на http://localhost:13001. При работе с VM нужен отдельный туннель с Mac:

```bash
tsh ssh -N -L 13001:127.0.0.1:13001 admin_sts@sts-vm-06
```

Новый сервис не подключается к уже существующей установке Flowise других проектов. Если LiteLLM расположен во внешней Docker-сети, подключите только новый сервис Flowise к этой сети, сохранив имя `litellm` и разрешённый модельный псевдоним.

## Доступ к модели и создание потоков

Предоставьте **отдельный виртуальный ключ LiteLLM для Flowise**, ограниченный нужными моделями. Мастер-ключ и ключ поставщика в Flowise передавать не требуется. Размещение ключа в новом сервисе должно быть явно разрешено владельцем. Скрипт не читает существующий ключ бота.

Сохраните выделенный ключ в закрытом файле `runtime/bot/flowise_llm_key` (права `600`), затем:

```bash
docker compose exec bot python /tmp/setup_flowise.py --llm-key-file /app/state/flowise_llm_key
```

При новой установке создаются четыре редактируемых в интерфейсе потока: два основных — **STS Flowise — ЮрАгент**, **STS Flowise — ФинАгент** — и по одному потоку с суффиксом **— проверка** для каждого агента. Каждый содержит Prompt Template → ChatOpenAI → LLM Chain. `basepath` направлен на LiteLLM; модель берётся из `LEGAL_LLM_MODEL` / `FINANCE_LLM_MODEL` на момент создания. Изменения модели в `.env` не меняют уже созданные потоки: настройте их в Flowise. Повторный запуск сохраняет существующие потоки.

Отдельный ключ Prediction API обязателен и сохраняется в `runtime/bot/flowise_api_key`; потоки не публичные. Flowise хранит зашифрованные учётные данные, запросы и ответы в своей базе. Том данных и ключ шифрования нужно резервировать вместе. Не передавайте реальные персональные данные в пилоте.

## Включение только тестовой комнаты

Создайте незашифрованную тестовую комнату в Element, пригласите `@bot:demo.local`. Возьмите идентификатор комнаты из её настроек. В `runtime/bot/flowise_setup.json` находятся идентификаторы созданных потоков. Создайте `runtime/bot/flowise_rooms.json`:

```json
{
  "!TEST_ROOM:demo.local": {
    "domain": "legal",
    "flow_id": "UUID юридического потока",
    "review_flow_id": "UUID юридического потока проверки"
  }
}
```

```bash
docker compose up -d --build bot
```

В логе должен появиться `Flowise pilot rooms configured: 1`. Отправьте содержательный вопрос по документам и дождитесь нового ответа. Запись `Flowise response received; domain=legal` подтверждает вызов Flowise; сама загрузка интерфейса этого не доказывает. Проверьте также обычную юридическую и финансовую комнаты и команду `!человек`.

Комнаты и роли изолированы: финансовый поток не вызывается для юридического маршрута. История других пользователей не передаётся. Потоки создаются без памяти; бот передаёт нужный контекст и выдержки источников. Обработка ответа остаётся общей с прямым LiteLLM. Flowise API не предоставляет здесь достоверный `finish_reason`, поэтому автоматическое определение обрыва по лимиту токенов ограничено.

## Отключение

Замените содержимое `runtime/bot/flowise_rooms.json` на `{}` и перезапустите **только бот**. Все комнаты вернутся к прежнему прямому LiteLLM. Остановка Flowise при включённом маршруте показывает ошибку сервиса; скрытой подмены ответа другой моделью нет.

Исторические отчёты про Multica сохранены как история проекта. Они не означают, что действующий бот её вызывает.

## Проверка без настоящего LLM-ключа

```bash
docker compose cp scripts/setup_flowise.py bot:/tmp/setup_flowise.py
docker compose cp scripts/check_flowise_transport.py bot:/tmp/check_flowise_transport.py
docker compose exec bot python /tmp/check_flowise_transport.py
```

Тест создаёт временный защищённый граф и модель-заглушку внутри сети контейнеров. Проверяет блокировку запроса без ключа, вызов графа с правильным ключом и сохранение метки `[S1]`, затем удаляет созданные объекты. В версии 3.1.4 ошибка Unauthorized обёрнута в HTTP 500; отсутствие вызова модели проверяется отдельно. Это проверка транспорта, а не качества ответов реальной модели и не полный тест переписки в Element.


## Раздельный черновик и проверка (13.10.2026)

Для обоих специалистов настроены два этапа. Основной поток делает черновик, поток **— проверка** получает этот черновик вместе с вопросом и теми же найденными выдержками и возвращает исправленный ответ. Это два вызова модели, как и прежде; дополнительный третий вызов не добавлен. При неудачной проверке цитат бот по-прежнему может повторить попытку. Некоторые проверенные типовые ответы обходят модель и Flowise вообще.

В интерфейсе http://localhost:13001 откройте раздел **Chatflows**:

| Поток | Что настраивать |
| --- | --- |
| STS Flowise — ЮрАгент | Понятное объяснение юридического вопроса и практические шаги |
| STS Flowise — ЮрАгент — проверка | Проверка нормы, условий, исключений и цитат черновика |
| STS Flowise — ФинАгент | Объяснение финансового вопроса, условий продукта и действий |
| STS Flowise — ФинАгент — проверка | Проверка сумм, сроков, комиссий и соответствия источника |

В блоке **Prompt Template → Template** меняются дополнительные инструкции выбранного этапа. Сохраните переменную `{request}`: бот подставляет туда вопрос, инструкции и выдержки. В **ChatOpenAI** меняются параметры генерации и разрешённый модельный алиас. После сохранения новый запрос использует изменения без перезапуска бота. Ключ LiteLLM сейчас ограничен существующим алиасом; ввод другого имени сам по себе не выдаёт доступ к новой модели.

Для аккуратной настройки меняйте один этап за раз, проверяйте те же вопросы и сохраняйте прежний граф. Изменения через UI хранятся в базе Flowise и **не появляются автоматически в GitHub или локальных JSON**. Не экспортируйте credentials в репозиторий. Исходные профили без секретов — `matrix_support_bot/agents/flowise_profiles.json`, проверка и применение — `flowise_profiles.py` и `scripts/upgrade_flowise.py`.

Пример обновления существующих простых потоков (в контейнере после копирования скрипта):

```bash
python /tmp/upgrade_flowise.py --state-dir /app/state --plan-file /app/state/stage-upgrade.json
python /tmp/upgrade_flowise.py --state-dir /app/state --plan-file /app/state/stage-upgrade.json --apply
```

Первый вызов только сохраняет закрытый план: прежние графы и настройки маршрутов. Второй проверяет, что настройки не менялись, обновляет инструкции в двух прежних графах и создаёт два защищённых потока проверки с существующими credential ID и ключом Prediction API. Новый LLM-ключ не считывается и не переносится. Скрипт принимает только известный граф из трёх узлов, чтобы не уничтожить ручные изменения сложной схемы. После применения перезапустите только бота для чтения маршрутов.

```bash
python /tmp/upgrade_flowise.py --state-dir /app/state --plan-file /app/state/stage-upgrade.json --rollback
```

Откат возвращает прежние графы/маршруты и удаляет только созданные этим планом потоки проверки. Он откажется перезаписывать независимые изменения администратора. Незавершённый apply тоже можно откатить. Резервный файл содержит внутренние настройки: храните его вне Git с правами `600`. На текущей VM состояние находится в `/app/handoff_state`, а план — `flowise-stages-plan-20261013.json` в этом каталоге.

Маршрут `review_flow_id` необязательный: старые конфигурации продолжают работать через один граф. Сеансы черновика и проверки разделены. Проверка моделью не является независимой юридической экспертизой; в этой установке оба этапа используют один алиас. Знания, выбор источников, окончательная проверка цитат, HTML-оформление и передача сотрудникам остаются в Python. Выбор комнат задаётся в `flowise_rooms.json`; типовые проверенные ответы могут обходить генерацию независимо от маршрута.


## Основные чаты через Flowise (13.10.2026)

Основными остаются существующие комнаты **STS — ЮрАгент — право** и **STS — ФинАгент — финансы**. Их идентификаторы сохранены, поэтому участникам не требуется переходить в другую комнату. Сначала они использовали отдельные Chatflows черновика и проверки; текущий маршрут заменён Agentflows V2, описанными ниже. Команды `!человек`, `!сотрудники`, `!другой` обрабатываются Python-ботом до обращения к модели.

Дополнительные комнаты с пометкой «Flowise (тест)» остаются подключены к **тем же потокам**. Это не изолированный стенд: изменение графа в Flowise влияет на все комнаты с его ID. Для независимых экспериментов сначала создайте копии потоков и отдельные маршруты. Эта операция не меняет состав участников, названия комнат или их историю.

Переносимая команда для новой установки после создания четырёх потоков:

```bash
docker compose cp scripts/enable_flowise.py bot:/tmp/enable_flowise.py
docker compose exec bot python /tmp/enable_flowise.py --state-dir /app/state
docker compose exec bot python /tmp/enable_flowise.py --state-dir /app/state --apply --backup-file /app/state/flowise-main-before.json
docker compose restart bot
```

Первый вызов показывает только число основных и итоговых комнат. Второй сохраняет закрытую резервную копию маршрутов и добавляет существующие основные комнаты по `room_routes.json`. Он требует оба департамента, четыре различных ID потоков и останавливается при конфликте специальностей. Дополнительные комнаты сохраняются. Повторное включение не перезаписывает резервную копию.

На текущей VM используйте `--state-dir /app/handoff_state --main-routes /app/room_routes.json`; резервная копия называется `flowise-main-before-20261013.json` внутри каталога состояния.

```bash
python /tmp/enable_flowise.py --state-dir /app/state --rollback --backup-file /app/state/flowise-main-before.json
```

После отката снова перезапустите бота. Независимые изменения маршрутов блокируют автоматический откат. Если нужно откатить также разделение черновика и проверки, сначала откатите подключение основных комнат, затем примените откат `upgrade_flowise.py`.


## Текущие Agentflows V2 (13.10.2026)

Откройте **Agentflows**, а не Chatflows. Активны два защищённых потока:

- **STS Agentflow V2 — ЮрАгент**
- **STS Agentflow V2 — ФинАгент**

Схема каждого: **Вопрос из Element → Контекст и локальные источники → ЮрАгент/ФинАгент → Проверка фактов и условий → Ответ в Element**. Это настоящие узлы Agentflows V2 установленной Flowise 3.1.4, а не переименование старых Chatflows. Один Prediction API запускает два последовательных вызова модели. Start не сохраняет память; Agent и LLM тоже не используют память. Бот сам передаёт ограниченный контекст продолжения. В агенте нет внешних инструментов.

В **Agent → Messages** меняйте дополнительные инструкции специалиста; в **LLM → Messages** — редактора. Сохраните выражения `$flow.state.*` и ссылку на результат предыдущего узла: они передают вопрос, источники и черновик. В **Model** каждого этапа — существующий LiteLLM и выделенный credential; другой алиас должен быть разрешён ключом. Системные и пользовательские сообщения теперь разделены по ролям. Поток не выполняет поиск: Custom Function только проверяет и разбирает пакет источников, подготовленный Python.

Основные две комнаты и дополнительные «Flowise (тест)» ссылаются на эти же два графа. Изменения графа затронут все его комнаты. Четыре прежних Chatflows сохранены для отката, но не вызываются при маршруте `engine: agentflow_v2`. Не удаляйте их до завершения испытаний. UI-изменения сохраняются в базе Flowise, не в Git.

Для новой установки сначала создайте защищённые Chatflows и выделенные credentials по инструкции выше; затем:

```bash
docker compose cp scripts/setup_agentflows.py bot:/tmp/setup_agentflows.py
docker compose exec bot python /tmp/setup_agentflows.py --state-dir /app/state --plan-file /app/state/agentflows-plan.json
docker compose exec bot python /tmp/setup_agentflows.py --state-dir /app/state --plan-file /app/state/agentflows-plan.json --create
# Проверьте созданные графы, не изменяя рабочие маршруты.
docker compose exec bot python /tmp/setup_agentflows.py --state-dir /app/state --plan-file /app/state/agentflows-plan.json --activate
docker compose restart bot
```

Первый запуск только готовит закрытый план. Create создаёт два непубличных Agentflows с прежними credential ID и ключом Prediction API. Activate проверяет графы и прежние маршруты перед переключением; комнат, участников и историю не меняет. На текущей VM каталог состояния `/app/handoff_state`, план `agentflow-v2-plan-20261013.json`. Этот файл хранится вне Git с правами 600.

Откат выполняется до удаления нового кода:

```bash
python /tmp/setup_agentflows.py --state-dir /app/state --plan-file /app/state/agentflows-plan.json --rollback
docker compose restart bot
```

Он возвращает прежние маршруты и удаляет только два созданных этим планом потока. Независимые изменения графов/маршрутов блокируют автоматический откат. Изменённые вручную графы нужно сначала сохранить и согласовать.

Проверка транспорта без реального ключа модели:

```bash
docker compose cp scripts/check_agentflow_transport.py bot:/tmp/check_agentflow_transport.py
docker compose exec bot python /tmp/check_agentflow_transport.py
```

Она временно создаёт граф, тестовый ключ и credential-заглушку, проверяет два этапа, роли, источники, разделение сеансов и запрет вызова без ключа, затем удаляет тестовые объекты. Проверка не отправляет Matrix-сообщения и не заменяет оценку реальной модели.
