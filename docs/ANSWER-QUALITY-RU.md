# Как устроена проверка полезного ответа

ЮрАгент и ФинАгент остаются в отдельных комнатах Element и используют отдельные Agentflows V2. Типовые расчёты, справка и некоторые ответы по источникам выполняются локально. Остальные вопросы проходят защищённый поток Flowise через LiteLLM.

## Два разных требования к ответу

1. **Ответить по существу.** Объяснить разрешение, ограничение, отличие понятий, применимый шаг либо дать запрошенный черновик. Корректная цитата рядом с посторонним советом не означает, что вопрос решён.
2. **Подтвердить проверяемые факты.** Для нормы, суммы, срока, обязанности и исключения нужны подходящие выдержки и условия применения. Организационный совет не превращается в правовую обязанность.

Проверка смысла остаётся модельной и может ошибаться. Код проверяет структуру, связь с выбранными утверждениями, цитаты и числовые отношения. Это не экспертное заключение юриста или финансиста.

## Что меняется в Agentflow

Проверяющая модель возвращает `answer_unit_ids`: номера предложений черновика, которые непосредственно решают задачу. Для определения, сравнения и вопроса о допустимости требуется подтверждённое объяснение, если источники найдены. При отсутствии источников разрешены конкретные безопасные действия без выдуманных норм.

Если ответа по существу нет, существующая ветка доработки получает `main_question_unanswered`. После удаления неподтверждённых предложений код проверяет, сохранилась ли основная часть. Нельзя получить успешный результат, оставив случайную цитату или потеряв все выбранные основные строки. Контракт без `response_goal` сохраняет совместимость с прежними потоками; новый контекст требует новый результат проверки покрытия.

Существенное условие не отделяется от вывода ради красивого ответа. При отсутствии исключения зависимая правовая часть отсеивается. Независимые подтверждённые факты и подходящие действия могут сохраняться. Неподтверждённые числа в оговорку не переносятся.

## Первоисточники и разъяснения

Редакторский план помогает объяснить связь положений. В него включены ограничения применения и ссылки на ID переданных первоисточников. План не получает отдельный S-ID и не может подтверждать юридическое утверждение. Для подтверждения всё равно выбираются выдержки исходных документов.

Для PDF добавлены ограниченные дословные окна через переносы строк. Иначе модель могла видеть основное правило и исключение на разных строках, а короткое заключительное слово вообще не имело выбираемой выдержки. Существующие Q-ID сохранены; добавляется не более восьми окон на фрагмент, каждое до 550 символов. Тексты корпуса и даты проверки документов не переписываются.

## Повторная проверка

Обычная локальная проверка не доказывает работу модели:

```bash
python scripts/evaluate_helpfulness.py --cases config/answer-goal-evaluation.json --output /tmp/answer-goals-local.json
```

Для реального прогона в окружении с настроенным доступом используется `--live flowise`. Этот оценщик может выбрать локальный ответ, поэтому в отчёте нужно смотреть число реальных вызовов. При сравнении изменений 03.11 отдельно принудительно проверялся модельный путь, даже для вопросов с локальным ответом.

Не считать совпадение регулярных выражений доказательством юридической точности. При изменении эталонов сохранять старые результаты; экспертное одобрение отмечать только после реальной проверки специалистом.
