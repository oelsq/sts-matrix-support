# Регулярная проверка и подготовка обновлений знаний

В активной базе 106 материалов. Это выборка, а не всё законодательство Казахстана. Добавление новых файлов и проверка существующих редакций — разные операции.

## Что работает автоматически

`matrix_support_bot/knowledge_monitor.py` при запуске бота и каждые шесть часов проверяет целостность и возраст проверки активных документов. Файл `knowledge-freshness.json` сохраняется рядом с SQLite очереди. Для тарифов контрольный возраст — 7 дней, для других материалов — 30 дней. Это внутренняя политика проверки, а не юридический срок действия документа.

Новый `scripts/refresh_knowledge.py` — отдельный процесс с доступом только к публичным официальным источникам и архиву. Он не использует ключи модели, учётные записи Matrix или переписку. Бот продолжает отвечать в закрытой сети по активной базе.

Параметры находятся в `config/knowledge-refresh-policy.json`:

- запуск cron каждые шесть часов, на 17-й минуте, по часовому поясу сервера;
- не более 20 источников за запуск, тайм-аут сетевого обращения 10 секунд, предел всего процесса 15 минут;
- тарифы проверяются не чаще раза в сутки, законы — не чаще раза в семь суток;
- недоступные источники повторяются не чаще раза в сутки;
- при первом обходе важные законы и четыре тарифа получают приоритет; ещё не проверенные материалы не вытесняются бесконечными повторами;
- активные документы подключаются только для чтения; новые версии автоматически не активируются.

Интервал сетевой проверки и возраст последнего содержательного просмотра различаются. Успешная загрузка не изменяет `reviewed_on` и не доказывает, что отдельная норма применима к событию пользователя. Если внешний источник недоступен, состояние — `check_unavailable`; дата содержательной проверки остаётся прежней.

## Где хранится история на VM

Все файлы этой функции находятся в `/home/admin_sts/sts-matrix-support`:

```text
maintenance/
  run-knowledge-refresh.sh
  knowledge-refresh/
    latest-run.log
    inventory.json          # целостность и возраст активных материалов
    summary.json            # итог последнего законченного обхода
    latest.json             # последняя попытка по каждому источнику
    artifacts/<sha>.*       # снимки по хешу содержимого
    runs/<time>-<id>/
      active-manifest.json # точная активная база при начале обхода
      <document>.check.json
      <document>.*
      summary.json
```

Повторные одинаковые снимки используют жёсткие ссылки на один архивный файл; отдельные квитанции проверки сохраняются. Различающиеся снимки имеют разные хеши. Предыдущий снимок/квитанцию нельзя перезаписать через `check_source`: нужен новый каталог обхода. SHA проверяется повторно перед активацией.

Статусы:

| Статус | Значение |
|---|---|
| `snapshot_unchanged` | Полученный PDF/извлечённый текст совпал с активным снимком |
| `page_unchanged` | HTML совпал с ранее записанным HTML; это не правовая экспертиза |
| `candidate_changed` | Байты отличаются: нужен разбор редакции, условий и исключений |
| `manual_page_comparison_required` | Общая веб-страница требует ручного сравнения; её нельзя автоматически заменить на закон |
| `check_unavailable` | Загрузка/извлечение не выполнены, источник не объявляется актуальным |
| `review_due` в inventory | Срок содержательной перепроверки активного материала превышен |

HTML страницы и намеренно краткая памятка могут отличаться без изменения закона. Официальные каталоги Halyk и Freedom также скачиваются и архивируются: одинаковый каталог загружается один раз за обход. Изменение HTML помечается `catalog_changed_review_required`; отсутствие старой ссылки не объявляется отменой тарифа. Страницы с динамическим содержимым могут требовать ручной проверки. Для тарифов нужно проверять не только PDF, но и официальный каталог/дату действия. Для закона сохраняются переходные положения и сноски; новая редакция не отменяет необходимость проверять период события.

## Запуск и установка

Локально, с доступом к внешним официальным сайтам:

```sh
python scripts/refresh_knowledge.py --knowledge offline_knowledge --state runtime/knowledge-refresh --policy config/knowledge-refresh-policy.json
```

На VM установщик создаёт ровно один помеченный блок cron текущего пользователя, сохраняя остальные задания:

```sh
python3 scripts/install_knowledge_refresh.py --root /home/admin_sts/sts-matrix-support
python3 scripts/install_knowledge_refresh.py --root /home/admin_sts/sts-matrix-support --apply
/home/admin_sts/sts-matrix-support/maintenance/run-knowledge-refresh.sh
```

Сначала нужен образ бота с `/app/knowledge_refresh.py`, `/app/knowledge_catalog.py` и `/app/tools/refresh_knowledge.py`, а также конфигурация в `project/config`. Задание использует текущий образ работающего бота, ограничено одним CPU и 384 МБ памяти. Если загрузка невозможна из сети VM, расписание сохраняет ошибки; сами новые редакции должны быть получены на разрешённом узле с доступом к источникам и переданы в проект с теми же квитанциями/хешами. Обход ограничений сети не выполняется.

## Активация проверенной редакции

Используется существующий `scripts/promote_knowledge_update.py`: просмотр кандидата и применимости → явная запись ответственного проверяющего → предварительная проверка → применение. Детали в [quality-program.md](quality-program.md). Старый файл и прежний манифест сохраняются. Автоматический процесс не выдаёт себя за специалиста и не создаёт экспертных одобрений.

После изменения активного корпуса нужно перестроить и проверить семантический индекс, выполнить поисковые/содержательные регрессии и установить согласованную версию на VM. До этого нельзя объявлять обновление законченным. Старый индекс с несовпадающим хешем корпуса не считается готовым.
